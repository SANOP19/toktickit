## 1. Peer Review Process & Rules Adherence

Throughout Sprint 3, our engineering team strictly enforces the core course collaboration rules:

1. **Rule 1 — Reviewer Merges PR (Strictly Enforced):** The author of a Pull Request (**@SANOP19**) **never** merges their own code. The assigned peer reviewer (from GitHub Collaborators & Teams) conducts a thorough review against the Acceptance Criteria, submits structured feedback, approves the PR, and clicks the green **`Merge pull request`** button into `lab3-staging`.
2. **Rule 2 — Reply to All Review Comments:** Every comment, suggestion, or question raised during peer review is answered and verified before merge approval.
3. **Rule 3 — Link PR to Issue:** Every PR is linked to its corresponding GitHub Issue using the GitHub Development panel to automate Kanban card movement.
4. **Rule 4 — Kanban Board Lifecycle:** All issues progress through the defined Kanban stages: `Backlog` → `Specified` → `Started` → `PR Review` → `Done`.
5. **Rule 5 — Staging Branch Strategy:** All feature branches (`feature/X-...`) originate from and merge into `lab3-staging`. The final release is prepared by merging `lab3-staging` into `main`.
